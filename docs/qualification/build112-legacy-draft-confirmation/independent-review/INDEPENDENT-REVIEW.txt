ATOMIC CUSTODY AND FAILURE HANDLING

Confirmation requires exactly one occupied draft slot. Equal dual slots and
conflicting slots are rejected untouched; sequential two-key writes are never
represented as atomic. One preference value holds exact content and confirmation
metadata. Before writing, the transaction compares the entire expected draft and
current context; after writing it checks the same slot and exact encoded record.

A write exception after taking effect, or a post-write context/readback failure,
revokes only the exact just-written confirmation record. Newer content/another
slot is not overwritten. The composer suppresses readiness on failed confirmation.
Storage errors remain failures; they never authorize a send or automatic retry.

The parent verified the locked shared_preferences 2.5.5 implementation uses
SharedPreferencesWithCache.setString returning Future<void>, not the old bool API.
The existing awaited adapter propagates native write exceptions. An earlier
question about a discarded bool was therefore resolved as not applicable; no
unnecessary adapter change was requested. Keep its dependency excerpt/hash with
the evidence. Cached readback alone is not claimed as a power-loss durability test.
